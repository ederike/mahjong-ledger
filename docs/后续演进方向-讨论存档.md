| 项 | 现状 |

## 2. 用户提出的四个方向（原话存档）

【原话】用户原话按语义分段保留：

> **方向一 · 积分板**
> 「我希望有一块屏幕，可以是手机屏幕，显示当前的积分情况，就像一块积分板一样。」

> **方向二 · 语音助手（含那句引发歧义的表述）**
> 「似乎也不需要每个人都拿手机登录这个网页了，直接有一个中心化的设备做统一的输入就可以。比如说，可以像呼喊小爱同学一样呼喊这个棋牌助手。比如打完一局呼喊，然后告诉他情况，助手就自动处理。」

> **方向三 · 摄像头**
> 「后面可以做一个摄像头，拍着牌局。可以根据场上情况和每局结束情况，说一些话活跃。然后每局结束，它可以通过视觉自动看牌面的结果记分。」

> **方向四 · 设备联动**
> 「再进一步就是，它可以连接棋牌设备，直接在开场通过语音调整棋牌桌的打法和张数。」

**【原话｜关键澄清】** 用户随后明确指出：

> 「不是啊，不是要做成一台设备统一输入，只是可以一台，可以有这样的用法。」

**这句澄清是本次讨论的最高优先级裁定**：
- 方向二是**新增一种可选用法**，不是**替换**现有「多人各自手机记分」的形态；
- 字面上的「不需要每个人都拿手机…直接有一个中心化的设备做统一的输入就可以」容易被读成架构范式切换，但用户最终口径是「**可以有**」；
- 因此：**不引入「中心设备」这个角色，不改动写权限模型，不砍掉任何现有用法**。多种用法并存。

## 3. 概念校正记录（两次误读，务必留档）

### 3.1 误读一：把「新增用法」读成「替换基线」

| | 内容 |
|---|---|
| 错误理解 | 「方向 2 把需求基线改了：多人写 → 单人写」；进一步推出「并发写入理由消失，事件溯源要换个理由留着」 |
| 用户纠正 | 「只是可以一台，可以有这样的用法」 |
| **【撤回】** | ①「多人写 → 单人写」的基线变更判断；②「并发理由消失」及其派生论证。**多人写仍在，并发写入根本没消失**，append-only 账本与无锁模型照旧 |
| **【确认】** | 叠加、并存、可选；不需要模式开关、不需要房主/独占锁、不需要权限模型变更 |

### 3.2 误读一的附带结论（同样撤回）

【撤回】「事件溯源的理由要从『并发不覆盖』换成『语音可纠错』」——这个**结论本身**（可纠错性有价值）没错，但**推理前提**错了：并发理由并未消失，只是**又多了**一条语音纠错的理由。正确表述是「理由叠加，不是理由替换」。

### 3.3 事实补充（【确认】，由代码核验得出）

**「一台设备记」在现有系统里已经成立，无需任何代码改动**：`winner` 每局在表单里选，`author` 只是记录者标签，且所有人都能写。今天拿一台手机放桌上、全桌轮流用它记，账就是对的。S2 要补的只是**让这种用法更顺手**（语音、常亮、大按钮），不是引入新架构。

### 3.4 仍然成立的判断（【建议】，未被纠正）

以下三条与「几台设备」无关，故不受校正影响，保留：

| # | 判断 | 状态 |
|---|---|---|
| A | **确认环节**是整条路线的核心矛盾：感知层若自动落账，等于让概率输出直接写账，与「LLM 不算分」同类问题 | 【建议】 |
| B | **「会说话」与「会看牌」应拆开**：气氛播报只需账本里的结构化数据，不需要摄像头 | 【建议】 |
| C | 积分板应发**只读令牌**，但性质是「纯输出通道」，不是替代多人写 | 【建议】 |

## 4. 架构主线（【建议】）

### 4.1 一句话总判断

> 这四步**不是四个功能，是「输入通道 + 输出通道」的逐级替换**；账本、计分内核、结算、统计四块一次都不用重写。前面立的「LLM 只出结构化字段、绝不产分数」这条边界，可一路延伸到语音、视觉、硬件。风险不在后端，全在**感知层**与**确认环节**。

### 4.2 恒定层（四步全程不动）

```
append-only 事件账本  ·  scoreRound() 纯函数  ·  零和断言
·  minTransfers() 结算  ·  统计/排行榜/走势
```

### 4.3 贯穿原则

> **感知层只出候选，落账必须确认；计分永不交给概率模型。**
> 确认的**成本**可以降（从点按钮降到一句「对」，甚至降到「先落 + 一句话撤销」），但确认这个**语义**不能消失。

### 4.4 两个正交维度（校正后的正确模型）【建议】

| 维度 | 取值 | 关系 |
|---|---|---|
| **谁在记** | 各自手机 / 桌上一台 / 混合 | 任意，打牌中途可随时变化 |
| **怎么记、在哪看** | 手点 / 语音；各自小屏 / 一块积分板 | 可插拔通道 |

**两者互不约束**。这是「可以有这样的用法」的准确架构表述：能力是叠加的、正交的，不是互斥的模式切换。

### 4.5 并存用法矩阵【建议】

| 用法 | 谁记 | 在哪看 | 是否需要改动账本 |
|---|---|---|---|
| A 各自手机（现状） | 各自设备，任意人可写 | 各自小屏 | 否（已支持） |
| B 桌上单设备 | 同一台轮流记 | 同一台 | **否（已支持）** |
| C 单设备 + 大屏 | 一台记 | 一块只读积分板 | 否 |
| D 混合 | 手机 + 桌上那台 | 各自小屏 + 大屏 | 否 |

> 四种可同时成立，无需开关。

## 5. 分阶段详述

> 阶段编号是【建议】的讨论编号，非排期、非承诺。每阶段的「状态」均为 **未开工**。

### S1 · 积分板（只读大屏）

| 项 | 内容 |
|---|---|
| 来源 | 【原话】方向一 |
| 目标 | 一块屏幕（可以是闲置手机/平板）常显四家当前积分、局数、庄家；局末可切到结算卡片 |
| 新增输入 | 无（沿用现有网页） |
| 新增输出 | 只读大屏页面，如 `/board?room=XXX`，大字高对比、横竖屏适配 |
| 账本改动 | **零**。`fullState()` 已返回 `net` / `stats` / `settlement` |
| 确认关卡 | 无（只读） |
| 工程量 | 【建议】最小，性价比最高 |

**坑（【建议】）**：
- `sharecode` 是唯一凭据且**可写**，把 URL 投到大屏 = 公开凭据且可被改账。应引入**只读令牌**，语义上也更对：屏只显示、不能写。
- 现有 4 秒轮询够用，但「刚落账立刻亮一下」体感更好，可考虑 SSE 或缩短轮询。
- 大屏常亮需求（Wake Lock / 设备设置），不能记一局解一次锁。

### S1.5 · 局末气氛播报（建议从 S3 前移）

| 项 | 内容 |
|---|---|
| 来源 | 【原话】方向三前半句「说一些话活跃」 |
| 拆分理由 | 【建议】**它不需要摄像头**。账本里已有连胜、逆转、单局最大分、谁今天最惨、谁刚摸满 6 张马 |
| 链路 | 局末事件 → 拼结构化摘要 → LLM 生成一句吐槽 → TTS 播报 |
| 账本改动 | 零 |
| 工程量 | 【建议】小，且立刻有体感 |

**设计约束（【建议】）**：只在**局末触发**，不在牌局中随时插话；播报内容只用账本结构化数据，不引入牌面隐私。

### S2 · 语音记分闭环（「喊一局」）

| 项 | 内容 |
|---|---|
| 来源 | 【原话】方向二；**并受 §2 澄清约束：这是可选用法** |
| 目标 | 打完一局喊一声、口述情况，助手自动处理到落账 |
| 新增输入 | 任意客户端可挂的语音通道：唤醒/按键触发 + ASR + 现有 `/parse` |
| 新增输出 | 语音复述（TTS）确认 |
| 账本改动 | **零**。复用 `POST /api/rooms/:code/parse`（预览不落账）+ 现有 `events` 落账、`correct`/`void` 纠错 |
| 确认关卡 | **【待定】** 见 §7-Q1 |

**确认形态的两种候选（【建议】，二选一或可切换）**：

| 方案 | 交互 | 代价 |
|---|---|---|
| 复述确认 | 念「东家鸡胡有鬼、中马两匹，东 +10…对吗？」→ 一句「对」落账 | 多一轮对话，错了当场拦住 |
| 先落 + 一句话撤销 | 说完直接落账，错了喊「撤销上一局」 | 最顺口；依赖账本可撤销 + 有人盯板 |

> 现有 `correct` / `void` 追加事件已支持「上一局不算」「刚才那局改成七对」「马是 5万不是 6万」，无需新机制。

**坑（【建议】）**：
- 「不需要每人拿手机」≠「不需要设备」，只是 N 台变 1 台**常开**设备；但按 §2 澄清，**这不排斥其他设备继续存在**。
- 浏览器 Web Speech 做不到真·始终在线唤醒（需用户手势、需前台）；现成音箱开放技能平台对自定义 LLM 限制较多。更现实路径：旧安卓机 / 小主机 + 开源唤醒词 + 本地 ASR。
- **牌桌洗牌声很吵，纯唤醒词易误触发**，「按一下再说」可能比常监听更靠谱。
- 单设备下 `author` 恒为同一身份，账是对的但「谁录的」不准；若要准，需每局自报或说话人区分（**不影响计分正确性**）。

### S3 · 摄像头：视觉候选 + 气氛

| 项 | 内容 |
|---|---|
| 来源 | 【原话】方向三后半句「通过视觉自动看牌面的结果记分」 |
| 目标 | 拍牌局，局末自动看牌面结果并记分 |
| 新增输入 | 视觉识别 → **候选字段**（预填，不落账） |
| 确认关卡 | **必须确认** |
| 工程量 | 【建议】**难度断崖，全路线最大** |

**关键结论（【建议】，需重点复核）**：
> 硬伤不只是识别难度，而是 **「有鬼 / 硬胡」「摸了几张马」「谁点的杠」属于规则状态与口头约定，牌面上根本没有**。纯视觉永远拿不全 `RoundInput`，因此**注定只能是「预填候选 + 人确认」，做不到无人值守自动落账**。加之账错了没人能一眼发现，与「账要算得对」这一核心诉求直接冲突。

- 首版降级建议：只做「局末亮牌识别 → 预填胡法档位候选」，不做全场跟踪、不做自动落账。
- 前置依赖：固定摄像头位姿、光照、牌面朝向；需区分手牌（不可见）与胡牌时亮出的牌。

### S4 · 棋牌设备联动

| 项 | 内容 |
|---|---|
| 来源 | 【原话】方向四 |
| 目标 | 开场语音调整棋牌桌的打法和张数 |
| 新增输入 | 语音设置指令 |
| 新增输出 | 设备执行 + **回读确认** |
| 账本改动 | 零；但**规则配置须同源下发** |
| 工程量 | 【建议】取决于设备开放性，可能比 S3 更早落地 |

**判断与坑（【建议】）**：
- 看似最科幻，实则设置类指令**低频、离散、可回读、可确认**，比视觉可控。
- 市面绝大多数自动麻将机只暴露档位按键、无公开协议；具体形态【待定】（§7-Q2），决定是改固件、模拟按键还是调 API。
- **设备设置与账本规则必须同源**：否则「桌上打 144 张、账上按另一套口径」会分叉。仍以 `lib/rules.ts` 为单一真相源，设备只是执行端。
- **物理动作（洗牌/推牌）必须防误触发**，建议回读确认 + 可急停。

### S0 · 部署形态（横向议题，非阶段）

【建议】现有「沙箱起服务 + 分享链接」撑不起常开设备与常亮大屏。走向这些用法时，可能需要一台放在牌桌旁的**本地主机**（旧手机 / 树莓派 / 小主机）承载唤醒词、ASR、本地服务与投屏。好处：牌桌录音录像**不出局域网**，隐私更说得过去；也呼应「中心化部署 + 成员接入」的既有偏好。

> 注意：按 §2 澄清，这**不是**要求把系统改成本地单机，而是「可以有」的一个部署选项；云上链接 + 本地只做输入输出同样成立。【待定】（§7-Q3）

**与既有技术栈的关系（【建议】）**：该助手可视为 Agent 栈的一个小而完整落地产物——助手 = Agent，计分/账本/设备 = Tool，语音视觉 = 感知通道，规则 = Skill（自然语言操作手册）。ASR 可沿用既有 SenseVoice 选型（中文准确率高、带标点）。

## 6. 建议顺序（【建议】，与用户给出的顺序不同）

```
S1 积分板  →  S1.5 气氛播报  →  S2 语音闭环  →  S4 设备设置  →  S3 视觉
```

| 理由 |
|---|
| 前两步**零后端改动**却立刻改变牌桌体验 |
| S4 设置类指令比 S3 概率性识别可控得多 |
| S3 放最后，且首版只做「亮牌识别 → 预填候选 + 必须确认」 |
| **性价比最高的第一步是 S1**：工程量最小、不动账本、顺手补齐只读令牌 |

> 用户未对此顺序表态，仅为【建议】。

| **Q1** | **确认形态**：语音复述再说「对」，还是「说完直接落 + 一句话撤销」？或两者可切换？ | 决定 S2 交互骨架与落账时机 |
| **Q2** | **「棋牌设备」具体是什么**：普通自动麻将机（仅档位按键）/ 带屏智能桌 / 自可控硬件？ | 决定 S4 是改固件、模拟按键还是调 API |
| **Q3** | **中心设备放哪**：本地常开主机（数据不出局域网），还是继续用云链接、本地只做输入输出？ | 涉及隐私与部署形态 |
| **Q4** | **S3 的底线**：接受「自动预填 + 必须确认」，还是目标就是完全无人值守自动落账？ | 若是后者，需先讲清账目可信度的代价 |

**另有两项隐含待定（【建议】提出，尚未问过）**：
- 氛围播报的**语气/尺度**（是否允许吐槽、是否点名「最惨」）；
- 只读令牌的**粒度**（按房间、按会话、是否可撤销）。

## 8. 风险与边界

| 风险 | 说明 | 建议对策 |
|---|---|---|
| **账目可信度** | 语音 ASR、视觉识别均为概率输出；自动落账后错误不易被察觉 | 感知只出候选；落账前确认；计分始终走 `scoreRound()` + 零和断言 |
| **凭据公开** | `sharecode` 唯一且可写，投屏/外发即等于开放写权限 | 只读令牌；大屏与写端权限分离 |
| **隐私** | 牌桌录音、录像属敏感内容 | 优先本地处理；只在局末触发播报；不长期留存原始音视频 |
| **误触发** | 洗牌噪声、误唤醒；物理设备误动作 | 按键触发优先；设置类指令回读确认 + 急停 |
| **规则分叉** | 设备设置与账本规则不一致 | `rules.ts` 单一真相源下发，设备只做执行端 |
| **历史数据** | 各阶段若改动规则/张数 | 账本 append-only 且重放只累加冻结净分，历史房间不受影响（v1.2 / v1.4 已两次线上验证） |
